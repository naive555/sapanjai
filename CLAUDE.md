# CLAUDE.md

## What this repo is

**Sapanjai (HeartBridge)** — a multi-tenant B2B SaaS platform, **Go (backend) + Next.js (frontend)** in one monorepo. It starts from a platform-core template and business domains get added on top as new modules.

**What the core already provides** (all live end-to-end):

- **Auth** — `/auth/{register,login,refresh,logout,verify-email,resend-verification,me,forgot-password,reset-password}`: bcrypt (cost 12) password hashing, HS256 JWT access/refresh pair issuance, session create + rotation with token-family reuse detection (a reused/revoked refresh token revokes its whole family), Redis-backed access-token blacklist and login rate limiting (5 attempts / 15 min), best-effort audit logging of `user.register`/`user.login`. **Email verification and password reset** ride the same Redis-token + outbox pattern (`docs/10-transactional-email.md`): `register` inserts the user row and its verification email into `email_outbox` in **one transaction**, so a user can never exist without its mail queued. Tokens are 32 CSPRNG bytes stored SHA-256-hashed in Redis and `GETDEL`-consumed, so redemption is single-use with no read-then-delete race. `POST /auth/verify-email` is deliberately a **POST, not a GET** — the frontend page at `/verify-email?token=…` is the GET target and POSTs the token on, so a link scanner prefetching the page never burns it. `POST /auth/forgot-password` **always** returns `200 { success: true }` — unknown address, known address, and active cooldown are indistinguishable, which is why there is no `RESET_TOO_SOON` code. A successful reset also sets `is_verified = true` (reaching the link proves mailbox control) and revokes every session for that user; already-issued access tokens survive to their own ≤15-minute expiry. `GET /auth/me` is what surfaces `isVerified` to the frontend — it is read fresh from the database and deliberately **not** a JWT claim, which would go stale for a full access-token lifetime after verifying. Verification is a **banner, not a gate**: nothing in the backend checks `is_verified`. Audit actions: `user.email_verified`, `user.password_reset_requested`, `user.password_reset`.
- **Organizations** — `POST /organizations` (create + owner membership in a tx), `GET /organizations` (caller's memberships with embedded org), `GET /organizations/members` (active org's member roster), `POST /organizations/invite` (role check + `max_members` plan-limit enforcement), `DELETE /organizations/members/:userId` (role check + cannot-remove-owner), with best-effort `org.created`/`org.member.invited` audit logging. All `RequireAuth`/`RequireOrg`-guarded.
- **RBAC** — `/rbac/{roles,assign}`: create/list/update-permissions role CRUD-lite + role assignment. `RequirePermission(action)` implements `*`/exact/`resource:*` semantics with owner bypass; its first production caller is the Connectors module below.
- **Subscription** — `GET /subscription` (the active org's subscription with its plan embedded) plus `GET /plans` (`RequireAuth`-only, not org-scoped), a read-only catalogue the tenant subscription page renders alongside the org's current plan. **Read-only by design**: the template's `POST /subscription/assign` was removed because it sat on `RequireOrg`, which is membership-only — any `member` could move their own org onto any plan and lift `max_members`/`max_roles`/`max_connectors` on themselves. Assigning a plan is `POST /admin/organizations/:orgId/plan`, superadmin-only. `subscription.Service.AssignPlan` and `EffectiveLimits` survive as the shared implementation the admin module calls — this module never reimplements the upsert.
- **Audit logs** — `GET /audit-logs`, filterable by `userId`/`action` with a capped `limit`, `RequireOrg`-guarded.
- **Connectors** — `/connectors` CRUD + `/connectors/:id/health-check`: org-scoped upstream connections (DB creds, API keys, ...) for the Managed MCP Gateway pivot (`docs/05-mcp-gateway.md`), gated by `RequirePermission("connector:{read,write,delete}")`. `config` is sealed at rest with envelope encryption (`internal/shared/envelope`: a fresh AES-256-GCM data key per row, wrapped by `CONNECTOR_MASTER_KEY`) and never returned by any endpoint or written to a log. `type` accepts `"generic"` (the original skeleton placeholder — no adapter, health-check always 501 `HEALTH_CHECK_UNSUPPORTED`) and `"google_sheets"` (`internal/adapter/googlesheets`, `docs/06-sheets-adapter.md`, `docs/07-sheets-adapter-decisions.md`) — the first real adapter, with a registered `connector.Checker` that refreshes the OAuth token and probes an allowlisted spreadsheet/folder. More per-type integrations (FlowAccount, PEAK, ...) land the same way.
- **MCP gateway** — `POST /mcp/:connectorId` (`internal/module/mcp`): one Streamable HTTP MCP endpoint per connector, stateless JSON, authenticated by a bearer MCP key (not a JWT). A fresh `*mcp.Server` per request registers only the tools the caller's RBAC principal (intersected with the key's own `scopes`) is permitted to use, so a denied tool never appears in `tools/list`; a second, call-time check re-verifies on every `tools/call` so a permission change takes effect on the very next call. Backed by a Redis token-bucket rate limiter per connector (`mcp:ratelimit:<connectorId>`) and best-effort audit logging (`mcp.session.started`/`mcp.tool.called`/`mcp.tool.denied`/`mcp.ratelimit.hit`/`mcp.file.downloaded`). The shipped tool catalog is the `google_sheets` connector's six read tools (`sheets_list_spreadsheets`, `sheets_describe_spreadsheet`, `sheets_query_rows`, `sheets_read_range`, `drive_list_folder`, `drive_get_file`) plus two connector-type-agnostic tools, `sapanjai_describe_connector` and `sapanjai_whoami`; write tools are not built (`docs/07-sheets-adapter-decisions.md` §3). `drive_get_file` hands back a short-lived signed download link (`GET /mcp/files/:connectorId/:fileId`, TTL ≤ 15 min) whose HMAC key is derived from `CONNECTOR_MASTER_KEY` via HKDF-SHA256 (`internal/module/mcp/filelink.go`) — deliberately not a separate secret, and a master-key rotation invalidating in-flight links is a non-event given the 15-minute ceiling.
- **MCP keys** — `/mcp-keys` (`internal/module/mcpkey`): mint/list/revoke org-scoped Personal Access Tokens (`mcp_api_keys`, migration `00008`) that MCP clients present as `Authorization: Bearer sk_live_...`. Hashed with SHA-256 (not bcrypt — a PAT is 256 bits of CSPRNG output, not a low-entropy password; see `docs/07-sheets-adapter-decisions.md` §1 Decision 1), the raw token is returned exactly once from `POST /mcp-keys` and never stored or logged. `scopes` (nullable) narrows — never widens — the creator's live RBAC grant, re-resolved on every gateway request rather than cached on the key.
- **Admin** — `/admin` (`internal/module/admin`, `docs/11-admin-panel.md`): the platform-staff console, and the one deliberate exception to tenant scoping — every route reaches across all organizations, guarded by `RequirePlatformRole` rather than `RequireOrg`/`RequirePermission`. `users.platform_role` (`superadmin`/`support`/unset) is read fresh from the database on every `/admin` request, never a JWT claim — the same reasoning `GET /auth/me`'s `isVerified` already follows — so a demotion takes effect on the very next request rather than surviving a stale access token. Reads and impersonation are open to both roles; every mutation (plan/limit changes, org delete, platform-role grant, ban, plan CRUD) is superadmin-only, enforced by a second, separate `RequirePlatformRole("superadmin")` guard instance rather than a per-handler role branch, so a compromised support account cannot destroy anything. A ban is durable (`users.banned_at`, not a JWT-only revocation) backed by a Redis `banned:<userId>` fast-path cache with **no TTL**; nothing re-primes it from the database except a login attempt, so the worst case after a Redis flush is a banned user's already-issued access token surviving to its own ≤`JWT_ACCESS_EXPIRES_IN` expiry — bounded, because banning also revokes every session so the refresh path is already dead. The three destructive mutations (org delete, platform-role grant/revoke, ban/unban) re-verify the caller's own password first, rate-limited independently of login (`admin:reauth:attempts:<userId>`) — a session left open on an unlocked laptop, or a stolen access token, is not by itself enough. `POST /admin/users/:userId/impersonate` mints a 10-minute, non-refreshable, **read-only** token (an `imp: true` claim enforced once at `Guards.verify()` for any non-GET/HEAD/OPTIONS request, not per-route) and refuses any platform-staff target outright, closing off impersonation as a privilege-escalation ladder. The whole group additionally sits behind `ADMIN_IP_ALLOWLIST` — checked before `RequireAuth` even runs, so an off-network caller gets a plain 404, never a 403 that would confirm something exists to deny — and, once `ADMIN_REQUIRE_2FA=true` (the default), a TOTP step-up gate (`internal/module/admin/totp.go`) every route depends on except the three `POST /admin/2fa/{enroll,confirm,verify}` routes themselves. Non-goal, enforced by `internal/server/admin_integration_test.go` rather than review habit: no admin response ever carries decrypted connector `config`, a `password_hash`, or a `key_hash` — connector and MCP-key views are metadata only.
- **Background worker** — `cmd/worker`, a `worker.Job`-based scheduler (`internal/worker/`) running registered jobs on an interval behind a Redis lock (`worker:lock:<job>`, held for ~one interval so a multi-replica fleet still runs each job about once per interval — a failed run releases the lock immediately for an earlier retry), with per-run timeouts and panic recovery. Two jobs ship. **Session cleanup** (`internal/job/sessioncleanup/`) batch-deletes expired sessions and revoked sessions past a retention window (`SESSION_CLEANUP_*` env vars), backed by indexes on `sessions` from migration `00006`. **Email dispatch** (`internal/job/emaildispatch/`, `EMAIL_*` env vars) drains the `email_outbox` table from migration `00010` — claiming a batch with `FOR UPDATE SKIP LOCKED`, sending via `internal/shared/email`, then marking rows `sent` (bodies nulled) or backing them off to `failed` after `EMAIL_MAX_ATTEMPTS`, and pruning `sent`/`failed` rows past `EMAIL_OUTBOX_RETENTION`. Claiming is **lease-based, not a `sending` status**: the claim `UPDATE` pushes `next_attempt_at` forward by `WORKER_JOB_TIMEOUT + EMAIL_DISPATCH_INTERVAL` (floored at 60s), so a run that dies mid-flight leaves its rows claimable again when the lease lapses — self-healing, with no reaper to own. `RESEND_API_KEY` is read **only** by `cmd/worker`; the API renders and enqueues and never talks to Resend, which keeps that secret off the internet-facing service. The worker exposes its own internal `GET /health` on `WORKER_PORT` (job run/failure/skip stats) — not part of the public API contract — and ships in the same Docker image as the API, selected by overriding the container command (`compose.yaml`'s `worker` service, `k8s/worker/deployment.yaml`, and the worker service's start command on Railway — `docs/09-railway-deploy.md`). That image ends in `CMD ["/app/api"]` and deliberately sets **no `ENTRYPOINT`**: an exec-form entrypoint would make a command override *append* to `/app/api` rather than replace it, so the worker/migrate/seed services would silently start a second API — and hosts that expose only a "start command" (Railway) give you no way to reset the entrypoint.
- **Frontend** — Next.js dashboard (`apps/frontend/`, App Router + shadcn/ui + TanStack Query) with pages for every module (auth, organizations + switcher, members, RBAC roles, audit logs, subscription, MCP keys at `/mcp-keys`, connectors at `/connectors` including a `google_sheets` config form at `/connectors/:id/google-sheets`), a client-token/single-flight-refresh auth model, and a runtime reverse proxy at `app/api/[...path]/route.ts`.
- **Ops** — every route documented at `/swagger` (swaggo-generated, spec committed to `apps/backend/docs/`); a distroless production image (`gcr.io/distroless/static-debian12:nonroot`) with a dedicated `cmd/healthcheck` binary since distroless has no shell for `HEALTHCHECK`; `golangci-lint` (v2 config schema) in `make lint` and CI; k8s manifests in `k8s/`; CI jobs for lint, backend, frontend, and a docker build, with `release.yml` pushing to ghcr on CI success against `main`.

See [`README.md`](README.md) for the quickstart, [`apps/frontend/README.md`](apps/frontend/README.md) for frontend-specific details. `docs/` holds the design documents behind the core — read them before implementing anything that touches it.

## Ground rules

- **`docs/02-api-contract.md` is the source of truth** for the core routes, headers, status codes, and error messages. The Go backend must match it exactly for those routes; new business-domain routes belong in the contract too — add them there when you add them.
- Module convention: handler → service → sqlc queries per module (`auth`, `organization`, `rbac`, `auditlog`, `subscription`, `connector`, `health`, `mcpkey`, `mcp`). Services return `apperror` codes; a single Echo `HTTPErrorHandler` maps codes to HTTP responses. No HTTP concerns inside services. New domains follow the same shape — `mcp` is the one exception worth knowing about: its handler delegates to the MCP Go SDK's `StreamableHTTPHandler` for the JSON-RPC envelope itself, rather than binding a DTO and returning JSON directly.
- Auth guards are middleware: `RequireAuth`, `RequireOrg` (needs `x-organization-id` header + membership), `RequirePermission(action)`. Permission semantics: `*` > exact `resource:verb` > `resource:*` wildcard.
- Secrets stored at rest (currently: connector `config`) use envelope encryption via `internal/shared/envelope`: a per-row data key sealed by a `KeyProvider` holding the master key. The env-var-backed `EnvKeyProvider` is the only implementation today; a KMS/Vault provider is a one-line swap in `server.New`, not a caller-side change. Decrypted config must never leave the owning service — no response DTO field, no log line, no audit metadata.
- Master-key rotation is rotate-on-read, not a batch job: every sealed envelope carries the `kid` of the key that wrapped it, and `EnvKeyProvider` can hold retired keys (`CONNECTOR_MASTER_KEY_PREVIOUS`) for decrypt-only use. `Encryptor.OpenAndRotate` opens under whichever key the envelope names and, if that key is no longer primary, also returns a re-sealed replacement for the caller to persist (best-effort — a failed write just means the row offers the same rotation again next read). To rotate: generate a new key, move the current `CONNECTOR_MASTER_KEY` into `CONNECTOR_MASTER_KEY_PREVIOUS`, set `CONNECTOR_MASTER_KEY` to the new value, deploy — then drop the retired key once every row has been read at least once. As of this writing, `connector.Service` still calls plain `Open`; wiring it to `OpenAndRotate` and persisting the rotated blob is a follow-up (needs a narrow sqlc query that only touches `encrypted_config`, not `UpdateConnector`'s full row rewrite).
- Schema changes are additive-forward only: never edit an applied migration in `apps/backend/migrations/`, add a new goose migration and regenerate sqlc code (`make sqlc`).
- Audit-log writes are best-effort: log failures, never fail the request.
- Admin responses (`internal/module/admin`) never carry decrypted connector `config`, a `password_hash`, or an MCP key's `key_hash` — every admin DTO is mapped explicitly field-by-field from its sqlc row, never a struct embed, so a schema change can't silently widen what a staff console serializes. This is enforced by test, not review habit: `internal/server/admin_integration_test.go` seeds a connector whose sealed config contains a known secret, then walks every admin response (including nested objects) asserting both that none of those field names appears under any spelling and that the secret's raw bytes appear nowhere in the body — a leak under a renamed key still fails.
- Log redaction is centralized in `internal/shared/logger/redact.go`, wired into every logger via `slog.HandlerOptions.ReplaceAttr` — any attr key in the sensitive set (`authorization`, `password`, `token`/`access_token`/`refresh_token`, `cookie`, `secret`, `api_key`; matched case-insensitively, `-`/`_` stripped) logs as `[REDACTED]` no matter the call site. Add new sensitive keys there, not at call sites. Caveat: slog only exposes leaf keys, so **log individual fields, never a whole request/body struct** (`slog.Any("body", req)` would serialize `req.Password`). Request logging stays limited to method/uri/status/latency/request_id — no headers, no bodies — and the URI goes through `logger.SanitizeURI`.
- Redis keys: every key below is written with `REDIS_KEY_PREFIX` (default `sapanjai:`) prepended — the prefixes are named unprefixed here for readability, but nothing constructs a bare key. It exists because a Redis instance shared with a sibling project collides otherwise: `blacklist:`, `login:attempts:` and `verify:resend:` all come from the platform-core template that other projects derive from, so on a shared instance `login:attempts:<email>` is literally one counter for both apps. Key construction lives in five places — `internal/infra/redis/{auth,admincount,email,ratelimit}.go` and `internal/worker/lock.go`, each behind a small unexported `…Key()` helper so the prefix can never be applied on the write path and forgotten on the read path. (`admincount.go` is the one file among the five whose key is a `sha256hex` of a filter string rather than an entity id — see the `admin:count:` entry below.) The prefix must be **identical on api and worker** (they meet on `worker:lock:` and `blacklist:`), which is why it is a fixed default rather than derived from `APP_NAME`; changing it orphans every live key, which is harmless — the orphans expire on their own TTLs. It namespaces the *keyspace*, not the instance: `maxmemory` and eviction are instance-wide, so a noisy co-tenant can still evict our locks and tokens (see `docs/09-railway-deploy.md`). The keys: `blacklist:<accessToken>` (15 min), `login:attempts:<email>` (max 5 per 15 min), `worker:lock:<jobName>` (TTL ≈ job interval), `mcp:ratelimit:<connectorId>` (per-connector upstream-API token bucket, `MCP_RATE_LIMIT_PER_MIN` tokens/minute, idle TTL 2 min — `internal/infra/redis/ratelimit.go`, checked in `internal/module/mcp/service.go` before a `tools/call` dispatches), `verify:email:<sha256hex(token)>` (email-verification token, value = userId, 24h TTL, `GETDEL`-consumed so redemption is single-use with no read-then-delete race), `verify:resend:<userId>` (email-verification resend cooldown, `SET EX 300 NX`, 5 min), `reset:password:<sha256hex(token)>` (password-reset token, value = userId, 1h TTL, `GETDEL`-consumed), `reset:request:<email>` (password-reset request cooldown, `SET EX 900 NX`, 15 min — keyed by **email, not userId**, because `forgot-password` runs before the address is known to belong to a user, and an id-keyed cooldown could not cover the unknown-address path identically), `banned:<userId>` (durable ban fast-path cache, **no TTL** — an entry that silently expired would let a Redis-only ban lapse behind the database's back; only `Unban` clears it), `admin:reauth:attempts:<userId>` (password re-auth limiter on destructive admin mutations — org delete, platform-role change, ban/unban — 5 attempts / 15 min, independent of `login:attempts:` so burning one budget doesn't hand an attacker a fresh one on the other), `admin:2fa:<userId>` (step-up TOTP verification cache, 12h TTL — set by a successful `POST /admin/2fa/verify` and consulted by `RequirePlatformRole` on every other `/admin` route when `ADMIN_REQUIRE_2FA=true`), `admin:2fa:attempts:<userId>` (brute-force limiter on `POST /admin/2fa/verify`'s 6-digit code, 5 attempts / 15 min, independent of the reauth limiter above), `admin:count:<sha256hex(filterKey)>` (cached admin list/stats `COUNT(*)`, 30s TTL — keyed by the exact filter set so paging through one search doesn't re-count per page; a Redis failure falls back to counting directly rather than breaking the list). Both token namespaces store `sha256hex(32 random bytes)` as the key, never the raw token, so a `KEYS`/`MONITOR`/RDB dump yields nothing redeemable.
- Rendered email bodies contain live, single-use bearer tokens. **Never log an `email.Message`**, never put a body or a token in an error, and null `email_outbox.body_html`/`body_text` in the same statement that marks a row `sent`. The centralized redaction in `internal/shared/logger/redact.go` cannot help here — it matches attribute *keys*, and the token is inside a value. The one sanctioned exception is `email.LogSender` in a local `APP_ENV`, which prints the whole body so a developer can click the link without a Resend account; that branch is an **allowlist** of local env values, not "anything that isn't production", so a staging deploy with no `RESEND_API_KEY` fails loudly instead of logging tokens.
- Multi-step writes (org create + owner membership; session rotation) run in transactions.
- Background jobs implement `worker.Job` and are registered in `cmd/worker/main.go`. Job runs are guarded by a Redis lock (`worker:lock:<job>`, TTL ≈ one interval) so multiple replicas run a job about once per interval; a failed run releases the lock for an immediate retry. Job failures never crash the worker (panics are recovered).
- Frontend never calls the backend cross-origin: `app/api/[...path]/route.ts` is a runtime proxy reading `BACKEND_URL` per-request, deliberately **not** a `next.config.ts` `rewrites()` entry (those resolve at build time, not container-runtime). **No CORS middleware exists on the backend and none should be added** — the browser only ever calls same-origin `/api/*`.
- Frontend tokens: access token in memory only (never persisted), refresh token in `localStorage`, single-flight refresh on 401 (`apps/frontend/lib/api/client.ts`).

## Commands

```
make up        # start db + redis (docker compose)
make api       # run the Go API (terminal 1)
make web       # run the Next.js dev server on :4000 (terminal 2)
make worker    # run the background job runner (terminal 3, optional)
make migrate   # goose up          make seed   # default plans
make sqlc      # regen query code  make test   # go test ./... (backend only)
make swagger   # regen OpenAPI docs (swaggo)
make lint      # golangci-lint if installed, else go vet (backend only —
               # frontend lint/typecheck/test run from apps/frontend/: pnpm lint / pnpm exec tsc --noEmit / pnpm test)
```

No process manager runs backend + frontend (+ worker) together — `make api`, `make web`, `make worker` are separate terminals. Regenerating sqlc code requires the `sqlc` CLI (`go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest`); building/running the API does not. Full containerized stack: `docker compose up -d --build` (db, redis, api, worker, web).

## Environment

Copy `.env.example` → `.env` (git-ignored; only the template is tracked). One file serves both the host-side (`make api`/`make worker`, via godotenv) and containerized paths — compose passes the same `.env` to the api/worker services as `env_file` and overrides only the two host-specific URLs, `DATABASE_URL` and `REDIS_URL`, since only compose knows the `db`/`redis` service hostnames. Required: `DATABASE_URL`, `REDIS_URL`, `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` (min 32 chars), `CONNECTOR_MASTER_KEY` (base64, exactly 32 bytes — `openssl rand -base64 32`), `JWT_ACCESS_EXPIRES_IN` (duration, default 15m), `JWT_REFRESH_EXPIRES_IN` (**seconds**, default 604800), `PORT` (3000), `LOG_LEVEL`, `APP_ENV`. Optional: `REDIS_KEY_PREFIX` (default `sapanjai:`, normalised to end in `:`; prepended to every Redis key so an instance shared with another application cannot collide — must match on api and worker; an explicit empty value opts out), `CONNECTOR_MASTER_KEY_PREVIOUS` (comma-separated base64 keys, retired `CONNECTOR_MASTER_KEY` values kept decrypt-only during a rotation — see the envelope-encryption ground rule above), `MCP_RATE_LIMIT_PER_MIN` (default 60 — per-connector upstream-API token-bucket capacity, tokens/minute; see the Redis key conventions above and `docs/07-sheets-adapter-decisions.md` step 4). `APP_PUBLIC_URL` (default `http://localhost:4000` — the browser-facing **frontend** origin verification/reset links are built against, not the API; trailing slash trimmed), `ADMIN_IP_ALLOWLIST` (default unset/empty, which disables the check — comma-separated CIDRs gating the whole `/admin` route group before `RequireAuth` runs; parsed once at boot, a malformed entry fails startup rather than the first request; a wrong value locks every platform staff account out of `/admin` with no in-app recovery path, so test any change in staging first), `ADMIN_REQUIRE_2FA` (default `true` — gates every `/admin` route except `POST /admin/2fa/{enroll,confirm,verify}` behind a completed TOTP step-up; set `false` only for local development, where minting a TOTP enrollment for every throwaway seeded account is friction with no security benefit). Worker-only, all optional with defaults: `WORKER_PORT` (3001), `WORKER_JOB_TIMEOUT` (5m), `SESSION_CLEANUP_INTERVAL` (1h), `SESSION_CLEANUP_RETENTION` (720h/30d), `SESSION_CLEANUP_BATCH_SIZE` (1000), `RESEND_API_KEY` (unset ⇒ `LogSender`), `EMAIL_FROM` (`Sapanjai <noreply@localhost>`; must be on a Resend-verified domain in production or every send 403s), `EMAIL_DISPATCH_INTERVAL` (15s), `EMAIL_DISPATCH_BATCH_SIZE` (20), `EMAIL_MAX_ATTEMPTS` (5), `EMAIL_OUTBOX_RETENTION` (168h/7d).

## Testing expectations

- Unit tests per service with interface mocks for infra.
- Integration tests against real postgres+redis (CI service containers) encoding the contract in `docs/02` — every route × happy path × every error code.
- Auth edge cases that must be covered: refresh rotation, token-family reuse → revoke family, rate limit at 5 attempts, logout revokes all sessions + blacklists access token.
- MCP gateway edge cases that must be covered: a denied tool never appears in `tools/list`; a permission or connector-allowlist change takes effect on the very next call, not the next reconnect; a revoked/expired/unknown PAT is rejected (401, indistinguishable reasons); a tenant's connector/spreadsheet is unreachable from another org's key; a rate-limited or scan-budget-exhausted call ends cleanly (`IsError`/`scan_complete: false`), never a panic or a raw Go error.
